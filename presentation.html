1. Executive Summary

This proposal details an Azure-hosted infrastructure for Supreme Counselling for Personal Development serving two user groups:

  • Public clients — website, booking appointments, AI chat assistant
  • Internal staff (<20) — private RAG system querying company data

The architecture uses Azure Container Apps (pay-per-second consumption plan) fronted by Cloudflare for DNS, WAF, SSL, and rate limiting. Public and internal data are kept in separate storage — no shared databases, no complex RBAC.

The estimated monthly cost is ~BBD $140–240 depending on usage, with the primary variable being AI inference load. Staff access to the internal system has two options presented in Section 7 for your decision.

Design principles: Separation of concerns • Data sovereignty • Minimal overhead • Pay-per-use scaling • No over-engineering

2. Architecture Overview

Figure 1: Full infrastructure — Cloudflare → Azure Public → Azure Internal (VNet)

Layer 1 — Cloudflare (Edge) — Free Plan

  • DNS — proxied record resolution
  • WAF — OWASP rules, SQLi & XSS protection
  • SSL/TLS — Full (Strict) end-to-end encryption
  • Rate Limiting — per-device JWT cookie, 10 req/min on form endpoints
  • All public traffic routes through Cloudflare before reaching Azure

Layer 2 — Azure Public (no VNet)

  • ACA Environment (Consumption) — container orchestration, no VNet needed
  • Container App — Web SPA + API — Node.js serving frontend and /api/contact, /api/booking
  • Container App — Ollama — CPU-based chat inference and document embeddings
  • Container App — RAG API — public document ingestion and vector retrieval
  • Azure SQL Database (Serverless) — booking records (name, email, phone, date, time)
  • Azure Files — Ollama model persistence (~/.ollama)
  • Blob Storage — public RAG documents for embedding
  • Azure Container Registry — Docker image storage
  • Azure Communication Services — email notifications (provisioned separately)

Layer 3 — Azure Internal (VNet-Isolated)

  • Azure Virtual Network (10.1.0.0/16) — fully isolated
  • ACA Environment (VNet-injected) — containers inside the VNet
  • Container App — Internal RAG — company data query interface
  • Container App — Ollama (Private) — private inference on company data
  • Storage Account (Private Endpoints) — internal company docs + embeddings, traffic never leaves VNet
  • Staff access — see Section 7 for your two options

5. Security & Compliance

Perimeter Security

  • All public traffic passes through Cloudflare — DDoS, WAF, SSL
  • ACA ingress locked to Cloudflare IP ranges
  • No public IP for internal resources

Data Sovereignty

  • Public and internal data in separate storage
  • No shared database — no RBAC middleware needed
  • Internal storage via Private Endpoints — traffic stays in VNet
  • Data in US East region

Identity & Access

  • Public: JWT cookie for rate limiting (no auth)
  • ACA uses managed identity — no connection strings in code
  • Secrets stored as ACA secret references
  • Internal: VPN or Cloudflare Zero Trust (your choice)

Compliance

  • Azure: SOC 2, ISO 27001, HIPAA aligned
  • Cloudflare: SOC 2, ISO 27001, PCI DSS
  • Option to deploy West Europe for GDPR

Recommendation: For a team of <20, Cloudflare Zero Trust is the practical choice — it's free, staff access the internal RAG from any browser with their Google/Microsoft login, no VPN client needed. The only reason to pick the Azure VPN Gateway is if you need full network-level access to the VNet (e.g., staff need to SSH into specific resources, not just hit a web app). The Azure VPN can always be added later if needs change — a simple enable_vpn_gateway = true toggle in the OpenTofu config.

Appendix: Why Not Over-Engineer?

  • No AKS — ACA provides containers without control plane management
  • No Azure API Management — the web app routes its own API; rate limiting at Cloudflare
  • No shared database — public and internal data physically separated, no RBAC middleware
  • No device auth service — JWT cookies for rate limiting need no database
